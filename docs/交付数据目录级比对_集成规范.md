# 交付数据「目录级比对 + 案例场景归因 + 单版本自洽」集成规范（模拟数据版）

> 用途：把「信贷产品交付案件」的**源数据目录级比对**能力，集成进「金融资产接入与账务适配 Copilot」（fin-asset-copilot）。
> 本文档既是一段可直接粘贴进系统的 **System Prompt / 设计口径**，也是开发落地指引。
> **强制约束：全程模拟数据，禁止任何真实机构名、产品名、客户名、贷款单号、文件路径。**

---

## 0. 现状盘点（不要重复造轮子）

本 Copilot 已内置「交付案件四维度分析引擎」，位于 `src/lib/rules/caseAnalysis.ts`，数据模型在 `src/types/index.ts`：

| 已具备能力 | 代码落点 | 说明 |
|---|---|---|
| 结构校验（sheet 缺失/多余/表头错配） | `structureCheck()` | 以 `accountTemplates` 为准 |
| 新老版本差异 | `versionDiff()` | **仅** CaseFile ↔ 单个 reference CaseFile |
| 业务场景自洽（放款/还款/退款/余额/逾期） | `analyzeScene()` | 基于 `CaseFile.scene` + 各 sheet |
| 跨产品线类比 | `crossProduct()` | |
| 21 条历史注意点校验 | `validateBizRules()` | |
| 汇总 | `runCaseAnalysis()` → `CaseAnalysisResult` | store `ensureCaseAnalysis()` 挂载即算 |
| 模拟数据 | `src/data/caseFiles.ts` 等 | 虚构「示例资产方 A / 示例账务系统」 |

**待补齐的能力（本规范目标）**：上述引擎工作在「已解析的 `CaseFile` 对象」层。原始需求还有一层它没覆盖——
1. **原始 DAT 目录级比对**：直接比较两个交付目录（`ledgerFile-decrypt/JD{业务日期}{变体}/JD_{表}_{日期}.dat`）的全部日期 / 全部表 / 全部字段；
2. **跨案例 × 场景归因**：借助「案例主文件」的「日期→案例→场景」映射，把每条目录级差异定位到具体案例与场景；
3. **单版本日期流转自洽**：不跨版本，仅校验某版本自身——如某日「提前还款 + 连续多次还款」却余额不变、FLOW 表缺记录，须标红。

> 本规范即描述这层「DAT 源接入 → 目录级比对 → 归因 → 单版本自洽」，并**复用** `runCaseAnalysis` 做逐案例四维度校验。

## 1. 模块定位（在 Copilot 中的角色）

- 作为「案例文件」能力的**上游数据源 + 横向比对器**：
  - 上游：`模拟DAT生成器` → `DAT解析器` → `CaseFile[]`（复用现有 `AccountSheet`/`SceneRecord` 类型）。
  - 横向：`compareDeliveries(旧交付目录, 新交付目录)` → 目录级差异 + 案例×场景归因 + 单版本自洽。
- 与现有「差异与适配分析 / 分析报告」页面共享 UI 卡片与「模拟 AI 分析模式」标识（`isMock=true`）。

## 3. DAT 源格式与解析规则

### 3.1 格式
- 字段分隔符：`@!@`（连续分隔保留空字符串，对齐现有 `AccountSheet.rows`）。
- 路径规范：
  `[账目数据目录]/ledgerFile-decrypt/JD{业务日期}{变体}/JD_{表名}_{业务日期}.dat`
  `变体` 区分同一天不同交付口径（如 `41` / `42`）。

### 3.2 十二类账务表
`CUS` `CUSCREDIT` `QUOTAADJUST` `LOAN` `PLAN` `FLOW`
`COMFLOW` `REPAYMENTFLOW` `FEEADJUST` `CUSCHANGE` `QUOTAFEE` `CASHFLOW`

### 3.3 主键（匹配键）—— 严格遵守
| 表类别 | 表名 | 主键列 |
|---|---|---|
| 贷款类 | LOAN / PLAN / FLOW / COMFLOW / REPAYMENTFLOW / CASHFLOW | 第 2 列（索引 1）= 贷款单号 |
| 客户类 | CUS / CUSCREDIT / QUOTAFEE / CUSCHANGE / QUOTAADJUST | 第 2 列（索引 1）= 客户编号 |
| 费用调整 | FEEADJUST | 按业务场景条件匹配 |

> ⚠️ 客户类表主键是「客户编号」列，**不是**「客户名称」列。

### 3.4 模拟生成建议
`模拟DAT生成器` 产出两套交付目录（旧 / 新），并**植入可控差异**用于演示：
- 客户级：某额度字段、状态字段变化（覆盖全部案例）；
- 贷款级：如「下一付息日」字段整体偏移；
- 案例级：某案例存在系统性「逾期认定逻辑分歧」（旧版判逾期、新版判正常，导致本金余额固定偏差）；
- 在**新版**故意植入 1~2 处**单版本自洽矛盾**：如某场景日「提前还款 + 连续 3 次还款」，但贷款余额较上一日未变、FLOW 表缺对应记录。

## 4. 比对与归因引擎（核心新增）

新增 `src/lib/rules/deliveryCompare.ts`，导出：

```ts
// 目录级单表差异（区分行新增/删除/字段变更）
export interface SheetDateDiff {
  bizDate: string;          // 业务日期
  sheet: string;            // 表名
  insertedRows: number;     // 行新增
  deletedRows: number;      // 行删除
  changedRows: { key: string; field: string; oldVal: string; newVal: string }[];
}

// 跨案例 × 场景归因
export interface AttributedDiff {
  bizDate: string;
  sheet: string;
  field: string;
  oldVal: string;
  newVal: string;
  caseName: string;         // 命中案例主文件映射
  scenario: string;         // 命中场景事件
}

// 单版本日期流转自洽结论
export interface FlowConsistency {
  bizDate: string;
  caseName: string;
  ok: boolean;
  notes: string[];          // 如「提前还款+3次还款，但余额未变」「FLOW 缺 3 笔」
  risk: RiskLevel;
}

export interface DeliveryDiffResult {
  isMock: true;
  dateDiffSummary: { bizDate: string; sheet: string; changeType: string }[];
  sheetDateDiffs: SheetDateDiff[];
  attributedDiffs: AttributedDiff[];   // 案例×场景归因
  flowConsistencies: FlowConsistency[]; // 单版本自洽
  openQuestions: OpenQuestion[];        // 复用现有类型
}
```

### 4.1 `compareDeliveries(oldDir, newDir)`
1. 遍历两目录全部 `{业务日期}/{表}.dat`，按「日期 + 表 + 主键」对齐；
2. **精确区分**为行新增 / 行删除 / 字段级变更（禁止把字段变更误报为行增删）；
3. 输出 `sheetDateDiffs` 与 `dateDiffSummary`。

### 4.2 案例 × 场景归因 `attributeToCases(diffs, masterFile)`
- `masterFile` = `[案例主文件]` 的「日期→案例→场景」映射（模拟生成，结构同现有 `CaseFile.scene: SceneRecord[]`）；
- 把每条 `SheetDateDiff.changedRows` 归到 `caseName` + `scenario`；
- 未命中映射的差异单独列「未归因」分组。

### 4.3 单版本自洽 `checkFlowConsistency(caseFiles)`
- 对每个案例逐业务日期校验「行为 → 数据」因果链（**无需对比另一版本**）：
  - 放款后余额 = 放款额；还款后余额下降且 FLOW 有记录；
  - 某日标记「提前还款 + 连续多次还款」→ 余额应下降、FLOW 应有对应笔数；
  - 不符 → `flowConsistencies` 标 `ok:false` 并给出 `notes`。
- 复用现有 `analyzeScene()` 的余额自洽 / 还款流水自洽逻辑，下沉到「日期」粒度。

## 5. 关键避坑规则（写进引擎，避免返工）

1. **长标识数字禁止数值化**：贷款单号等 19 位标识必须**字符串原样比较**；`normalize()` 仅对 ≤15 位纯数字做数值归一，更长或非数值一律按字符串。否则精度丢失 → 主键失配 → 差异归零。
2. **客户表主键取「编号」列，不是「名称」列。**
3. **差异分类精确**：字段变更与行增删分开统计；配对按主键组内贪心匹配，避免顺序错位误判。
4. **「无差异的场景日」＝两版一致**，不要误判为「部分吻合」。
