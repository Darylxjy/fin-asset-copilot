01

产品定位与价值

Positioning

资产接入是消费金融机构与资金方合作的关键环节，核心交付物是一份份结构复杂、版本多变的账务文件 （含客户、借据、还款计划、流水、资金对账等多类 sheet）与对接方的接口文档。 产品经理需要在接入之初，快速判断「字段对不对得上、版本变没变、业务场景自不自洽、会不会影响其他产品线」，并收敛出需要人工确认的问题。

本产品把上述工作拆成确定性规则能跑的、语义理解要做的、 人必须拍板的三类，分别交给规则引擎、LLM（模拟）、产品经理， 最终沉淀为一份可评审、可导出、可追溯的分析报告。

为谁解决

  • 金融产品经理（资产接入 / 账务适配方向）
  • 需要对接口文档与账务文件做差异比对的需求/分析角色
  • 负责跨产品线接入一致性校验的架构/风控角色

带来什么

  • 把「逐字段人工比对」变成「规则自动跑、人只看结论」
  • 把散落的历史注意点沉淀为可程序化验证的知识
  • 把待确认问题收敛成人机协同闭环，结论可追溯
02

发现的真实业务问题

Problem

接口资料阅读成本高

  • 接口文档长、字段多，人工提取接口 / 字段 / 枚举 / 错误码耗时且易漏

内外适配判断复杂

  • 同名异义、异名同义、类型 / 精度 / 枚举不一致需逐项核对

账务文件版本变化比对困难

  • 新旧版本字段新增 / 删除 / 改名 / 改义，仅按字段名比较会漏掉「改名不改义、改义不改名」

账务 Demo 问题依赖人工发现

  • Demo 字段是否与文档一致、枚举是否越界、精度是否符合，需人工逐条校验
03

为什么 MVP 只先做账务文件适配

Scope

完整的资产接入平台包含接口文档解析、接口适配、账务适配、贷后适配、自动化配置等庞大范围。第一版不追求大而全， 而是先攻坚最机械、最易遗漏、ROI 最高的环节——账务文件及字段适配分析：

  • 账务字段数量大、版本变化频繁，人工比对成本最高；
  • 字段差异规则清晰，适合先用确定性规则引擎跑通链路；
  • 待确认问题天然需要人工介入，能自然体现 Human-in-the-loop；
  • 先验证「规则 + 语义 + RAG」的分工模式，再扩展到接口适配。
04

核心能力：案例四维度校验

Core Capability

本 Demo 还原了一条真实的资产接入交付链路：从多 sheet 源文件拆分为独立案例文件，再以账务文件文档为模板填充表头、按贷款单号从 DAT 填充数据，最后做全量校验。校验环节对应四个维度：

1结构一致性校验
以账务文件文档为基准，逐案例核对 12 个 sheet 是否齐全、表头字段是否与模板一致（集合差集检测，避免中间插列被误判为末尾追加）。
2新老版本差异对比
按文件名匹配，逐 sheet、逐字段、逐行对比：新增 / 删除 sheet、字段值变化、金额差异方向与大小；精度按金额类列对齐比较（2→4 位）。
3业务场景自主分析
读取场景 sheet 时间线，自主判断「该有的数据有没有、不该有的有没有、时间点与逻辑是否自洽」：放款 / 还款 / 结清自洽、退款无流水、余额 = 放款 − 已还本金、逾期罚息合理性。
4跨产品线类比 + 历史注意点
扫描其他产品案例，判断新场景是否影响现有产品线解析逻辑（如示例分期产品专用字段）；用沉淀的 21 条业务注意点逐条验证，输出通过 / 不通过 / 不适用。

⚠ 数据与免责声明

  • 本 Demo 全部数据为虚构脱敏（主体「示例资产方 A / 示例账务系统 / 示例分期产品」为虚构），禁止对应任何真实企业、产品或文件。
  • AI 分析为模拟（规则引擎 + 确定性叙事），页面全程标注「模拟 AI 分析（非真实大模型）」，未调用任何真实大模型 API。
  • 分析引擎使用内置虚构案例以保证演示确定性；「资料管理」上传的真实文件仅作只读预览，不反向驱动内置分析。
05

产品架构与技术方案

Architecture
文件上传→ 文件解析→ 字段结构化→ 规则引擎（确定性比较）→ 检索内部知识（RAG）→ LLM 语义与业务分析→ 结构化 JSON 输出→ 人工确认→ 分析报告

AI 与规则分工（核心设计原则）： 规则负责确定性判断（字段新增 / 删除、类型 / 长度 / 精度变化、必填规则变化、枚举增减、日期 / 金额格式、CSV 字段计数）； LLM 负责语义与业务（异名同义识别、业务含义变化、逻辑冲突判断、候选映射推测、系统影响分析、待确认问题生成）； RAG 提供内部上下文（我方字段定义、系统业务规则、历史需求、历史接入案例、已确认问题、历史映射关系）。

为什么 RAG 而非微调：内部接口 / 字段 / 规则变化频繁，通用大模型 + RAG + 规则引擎更跟得上迭代； 不同资产方文档差异大，需要可插拔上下文；且 RAG 天然可追溯，便于展示判断依据与知识来源，利于企业知识的隔离与治理。

Demo 第一阶段使用「规则引擎 + Mock AI 分析结果」：未配置模型 API 时明确标注「当前为模拟 AI 分析结果」，不假装调用大模型； 同时预留 analyzeWithAI(context) 接口，后续可接入通义千问 / OpenAI / Claude 等，API Key 不硬编码在前端。

10

Human-in-the-loop：AI 出错怎么办

Trust & Control

所有 AI 生成的关键判断都支持：接受 修改 驳回 标记待确认

人工反馈沉淀为「接受 / 修改 / 驳回 / 待确认」记录，可用于后续 Prompt 调优、规则完善、知识库更新与评测集扩充。 设计上始终体现：AI 是 Copilot，不是最终决策者；置信度过低或资料不足时允许输出「当前资料不足，无法判断」。
